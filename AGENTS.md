# Правила проекта Call Center Frontend

## Язык и коммуникация

- Отвечай на языке последнего сообщения пользователя.
- Документация проекта (`README.md`, `PLAN.md`, `docs/`) ведётся на русском языке.
- Имена API, переменных, маршрутов и кодовые идентификаторы сохраняй в оригинальном виде.
- Не показывай в чате diff, hunks, содержимое файлов или вывод инструментов редактирования. Сообщай только краткий статус, проверку и остаточные риски.

## Изменения и Git

- Не создавай коммиты автоматически. Коммит — только после прямой команды пользователя.
- Если коммит запрошен, используй только префиксы `feat:`, `fix:`, `refactor:`, `docs:`.
- Не откатывай чужие изменения и не используй разрушительные команды без явного разрешения.
- Перед изменением прочитай целевые файлы и делай минимальный связный набор правок.
- При редактировании соблюдай silent-editing: не выводи патчи в чат.

## Архитектура

- Соблюдай Feature-Sliced Design: `app` — маршруты и композиция, `widgets` — крупные блоки, `features` — пользовательские действия, `entities` — доменные модели/API/state, `shared` — общие инфраструктурные компоненты.
- Все каталоги и импорты чувствительны к регистру и используют lowercase. Не создавай параллельные `Order`/`order` или аналогичные деревья.
- Runtime-код не импортирует mock-данные из page-local каталогов. Mock-данные допустимы только для Storybook и изолированных визуальных тестов.
- API-контракт является источником истины. Не выдумывай поля, статусы или переходы; сверяйся с `../api-callcenter/docs/contracts`, `docs/openapi.yaml` и legacy-реализацией.
- Не переносите в браузер credentials Chef, MariaDB или production Redis. Frontend знает только публичный API URL и публичный ключ карт.

## Docker и проверка

- Основной воспроизводимый workflow — Docker Compose.
- Для разработки используй `docker-compose.dev.yml`; production-образ собирай через `docker-compose.yml`.
- Полные проверки запускай внутри frontend-контейнера, когда это возможно.
- Не объявляй проверку успешной без фактического результата команды. Отдельно указывай ошибки кода и ошибки окружения/registry.
- После связного шага проверяй как минимум `npm test` и `npm run build` в Docker; не запускай широкие или промежуточные проверки без необходимости.

## Документация и план

- Поддерживай `README.md` актуальным для запуска FE/API, CORS, env и Docker.
- Поддерживай `PLAN.md` как живой план миграции mock → API, с этапами, тестами и явно отмеченными блокерами.
- Не заявляй API полностью готовым, пока runtime-экран не использует типизированный API-клиент и не имеет тестов состояний loading/empty/error/success.
